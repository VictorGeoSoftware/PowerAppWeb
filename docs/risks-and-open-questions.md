# Risks and Open Questions

## Blocking Next Phase
- None.

## Implementation-Time Questions
- Backend `/user-data` checks device binding only when `phoneUuid` is sent; a client omitting it bypasses the one-device rule. Web must always send it (`device-binding-basic`); consider making it mandatory server-side before PROD.
- Real-phone testing before hosting: add the Mac's LAN IP to Firebase Auth authorized domains, or test on the hosted HTTPS URL.
- IONOS hosting details, domain, and TLS setup (same as BmWeb).
- Comparator calculation (decided in `comparator-calculation`): ported to the client (`src/lib/comparator/`). Risk: drift if BmApp's pricing rule changes. Mitigation: golden cases are generated by compiling the BmApp sources (`scripts/golden/generate-comparator-golden.sh`); regenerate after any BmApp comparator change and the golden test fails on drift.
- Backend changes: bill photo upload + extraction (done in `backend-bill-photo-extraction`: JPEG/PNG ~30–45 s end-to-end on local QA, 4000+ px photo 38 s), web push token registration (done in `web-push-registration`, BmBackend `qa`), device binding for web client type.
- Firebase web app registration in project `brielmarnysos-1dc68`.

## Later / Not MVP
- Pre-PROD: Bound Device hardening. Goal: prevent Brokers sharing accounts (Android and web). Problem: iOS may evict browser storage, losing the device id and causing false binding conflicts. Decide strategy before PROD release.
- Final stage: PWA install + Web Push.
- Offline support.
- Additional languages.

## Assumptions
- Development runs against BmBackend QA; all backend changes go to the `qa` branch.
- Until hardening, a simple persisted browser device id is acceptable in QA.
- Backend API contract used by Android is reusable as-is for web, except the items above.
- Brokers accept "one device total"; switching Android ↔ web needs an admin reset in BmWeb.

## Risks
- Dev machine on Volvo corporate network cannot reach BmBackend QA ("Application Blocked"); mitigated by the local Docker QA stack (`../BmInfra/bm-local-qa`, localhost:9081).
- `consumption-by-photo`: backend photo support is merged into BmBackend `qa` (#64); remote QA returns 400 → "No se pudo iniciar el estudio" until that `qa` is deployed. iOS HEIC→JPEG conversion via `accept="image/jpeg,image/png"` confirmed indirectly on a real iPhone (2026-10-16: camera shot uploaded and reached the report; HEIC would have been rejected locally). Not yet observed in a network log.
- Live in-browser CUPS OCR accuracy is lower than ML Kit; mitigated by photo-upload and manual-entry fallbacks.
- Accepted: iOS Safari OCR accuracy unverified until `qa-real-device-checks` (same bills, same thresholds); if it fails, `cups-camera-ocr` reopens. iOS may end the camera track when the tab is hidden — the scanner then shows "Reintentar cámara".
- Tesseract.js worker/core/lang data load from the library's default CDN (jsDelivr); offline or a blocked CDN shows "No se pudo iniciar el lector" (manual entry still works). Self-hosting is deferred to offline support (Later / Not MVP): without offline mode it does not affect installability.
- When OCR misreads the optional CUPS suffix (positions 21–22, frontier point), the parser returns the valid 20-char base; this identifies the same supply point and is not a false-valid.
- iOS PWA limitations (push only when installed, storage eviction, background tab throttling during polling).
- PWA installability: Lighthouse 12 removed the PWA audit; installability is checked by `e2e/pwa.spec.ts` through Chrome's `Page.getInstallabilityErrors` (same as DevTools → Application → Manifest). Real install on iPhone/Android needs the HTTPS QA deployment (`qa-real-device-checks`).
- Web Push: price updates are delivered by multicast to the stored tokens (not topics); dead tokens are pruned on `UNREGISTERED`/`SENDER_ID_MISMATCH`/`INVALID_ARGUMENT`, so stale rows (browser data cleared without logout) disappear on the next send. Every web push must show a notification (iOS revokes subscriptions that receive silent pushes), so unlike BmApp the web shows "Tarifas actualizadas" on each (debounced) price change. No force logout over web push (tokens are wiped with the grant). Raw FCM payload shape confirmed live in desktop Chromium; real iPhone/Android delivery is checked after deployment (`qa-real-device-checks`). Needs `NEXT_PUBLIC_FIREBASE_VAPID_KEY` in each deployment; FCM (`fcmregistrations.googleapis.com`) was reachable from the dev Mac on 2026-10-19. On QA, a price change sends to every QA web token, including developers' browsers. Risk: FCM also returns `INVALID_ARGUMENT` for an invalid message (e.g. payload > 4 KB), so one bad send could prune every token; if that is ever seen, only prune on it when not all tokens in a chunk fail with it.
- Calculation drift between Android and web if logic is duplicated.
- Local Docker QA can't complete a CUPS Consumption Job: no n8n/Datadis, and `docker-compose.yml` sets `N8N_WEBHOOK_URL` while BmBackend reads `N8N_FETCH_USER_CONSUMPTION_WEBHOOK_URL` (fix belongs to BmInfra/BmBackend). E2E mocks the job endpoints; the real end-to-end CUPS check needs a working n8n.
- PDF bills: Docling extraction must finish inside the 60 × 3 s (~3 min) poll budget, or the study times out (BmApp parity). Local QA, 2026-10-14: 2.0TD Iberdrola 54 s, 3.0TD Repsol 37 s. Watch real-world timings on the QA VPS.
- PDF bills on iOS: some Files providers report an empty MIME type; the client accepts any `.pdf` name. Pending a real check of the Files picker in iPhone Simulator Safari.
- BmBackend keeps jobs in memory: a backend restart loses in-flight jobs and the 1 h restore (status/result 404 → error or cleared id).
